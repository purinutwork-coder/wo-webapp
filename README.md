# wo-cf — เครื่องมือวัดของกองที่ 0 **ไม่ใช่โครงของระบบจริง**

> **โฟลเดอร์นี้ไม่ใช่จุดเริ่มต้นของระบบบน Cloudflare** · มันคือเครื่องวัดที่ใช้ตอบคำถาม
> ที่ยังไม่รู้คำตอบ ก่อนตัดสินใจว่าจะย้ายหรือไม่ย้าย · โค้ดในนี้ไม่มีชั้นสิทธิ์ ไม่มีชั้นตัวตน
> ไม่มีการตรวจข้อมูลนำเข้า และไม่เคยถูกออกแบบให้มี · **ห้ามเอาไปต่อยอดเป็นของจริง**
> ให้เริ่มโครงของจริงใหม่ตามแผนกองที่ 1

Worker ที่ deploy จากโฟลเดอร์นี้ **ถูกลบทิ้งไปแล้ว** เมื่อ 30-09-2026 พร้อมความลับทั้งสามตัว
ตามเงื่อนไขที่เจ้าของระบบตั้งไว้ว่า *"ของชั่วคราวที่ยังกดได้คือกับดักที่รอคนเผลอ"*
สิ่งที่เหลือไว้คือวิธีวัด เพื่อให้วัดซ้ำได้ด้วยวิธีเดิมตอนย้ายจริง

## ข้อควรรู้ที่ติดมากับการวัด — อ่านก่อนวัดซ้ำ

**นาฬิกาในตัว Worker วัดเวลาคำนวณของตัวเองไม่ได้** · `Date.now()` ไม่เดินเลยระหว่าง
การคำนวณที่ไม่มี I/O ซึ่งเป็นมาตรการกัน Spectre ของแพลตฟอร์ม · Worker รายงานกลับมาว่า
ใช้เวลา `0 ms` ทั้งที่วน SHA-256 ห้าพันรอบ · ทางที่ใช้ได้คือให้ทำงานซ้ำ K ครั้งแล้ววัดจาก
ฝั่งผู้เรียก เวลาเครือข่ายเท่ากันทุกครั้งจึงตัดกันหมด ส่วนต่างที่เหลือคือเวลาคำนวณล้วน

**ต้องนับเฉพาะคำขอที่ได้ 200** · คำขอที่ชนเพดาน CPU ตอบกลับ **เร็วกว่า** คำขอที่สำเร็จ
ถ้าเอาเวลามาเฉลี่ยรวมกันจะได้ตัวเลขที่ดูดีกว่าความจริง — เคยเกือบรายงานผิดมาแล้วครั้งหนึ่ง

**ชนเพดาน CPU หนึ่งครั้งแล้วพาทั้งตัวลง** · หลังจากนั้นคำขอถัดไปทุกคำขอตอบ 503
แม้เป็นงานเบาที่สุด จนกว่าจะเริ่มใหม่ · ไม่ใช่ตายเฉพาะคำขอที่หนัก

**คำขอแรกของแต่ละ isolate ใช้ 773 ms** (จับมือ TLS + DNS) แล้วที่เหลือ 40 ms

**เบราว์เซอร์ค้างอยู่หลังปิด** · ยิงออก PDF สามครั้งติดกัน สองครั้งหลังได้ 500
เพราะชนเพดาน 3 ตัวพร้อมกันของแผนฟรี · ถ้าหลายคนกดพิมพ์พร้อมกันจะมีคนไม่ได้ไฟล์

**ฟอนต์ไทยที่ได้คือ `Loma`** ไม่ใช่ตัวที่ขอไป (`Noto Sans Thai`, `Sarabun`) ·
เครื่องเรนเดอร์ถอยไปใช้ตัวที่ตัวเองมีโดยไม่บอกใคร · ฟอนต์ถูกฝังและตัดเฉพาะตัวที่ใช้มาใน
ไฟล์ (`FontFile2` หกชุด) **เครื่องปลายทางจึงไม่ต้องมีฟอนต์ไทย** แต่ถ้าอยากคุมหน้าตา
ให้เหมือนแม่แบบเดิม ต้องส่งไฟล์ฟอนต์ไปเองผ่าน `@font-face`

## เงื่อนไขที่ใช้ตอนวัด

- **anon key เท่านั้น** ไม่เคยมี service_role อยู่ใน Worker ตัวนี้
- ทุกคำขอไปฐานข้อมูลได้ **`http 401` พร้อม `42501 permission denied`** ซึ่งเป็นรหัสของ
  Postgres เอง แปลว่าเดินทางครบเส้นทางแล้วถูกปฏิเสธที่ประตู GRANT
  **ไม่ใช่การวัดเส้นทางเต็มรูปแบบ** — ที่ขาดคือการอ่านแถวกับแปลงผล
- ทุกทางมีด่านรหัสลับ 64 ตัวอักษร ปิดตายเมื่อยังไม่ได้ตั้งรหัส และเทียบแบบใช้เวลาเท่ากัน
- ไม่เคยเขียนอะไรลงฐานข้อมูล ไม่มีเส้นทางไหนเขียนได้

## กองที่ 1 ข้อ 2 — `fetch` เทียบ `UrlFetchApp` · วัดแล้ว 01-10-2026

วัดจาก Worker ที่ deploy จริง ยิง Supabase จริง · **colo BKK ทุกรอบ** · Worker ถูกลบทิ้งแล้ว
เครื่องวัดอยู่ใน `proof-batch1/` วิธีวัดซ้ำอยู่ใน `proof-batch1/วิธีวัด.md`

**ได้คำตอบครบทั้ง 6 ข้อ** · สามข้อแรกวัดได้รอบเดียว อีกสามข้อต้องเปลี่ยนเครื่องวัดก่อน
เพราะการยิง fetch ใส่ตัวเองถูก Cloudflare ปฏิเสธด้วย `1042` (เล่าไว้ข้างล่าง)

### สิ่งที่สำคัญที่สุดที่เจอ — SPEC เขียนผิด และโค้ดก็ผิดตาม

**GRANT ที่ขาดคืนมาเป็น `401` ไม่ใช่ `403`**

```
{"code":"42501","details":null,
 "hint":"Grant the required privileges to the current role with: GRANT SELECT ON public.work_order TO anon;",
 "message":"permission denied for table work_order"}        ← status 401
```

SPEC 22.2, 22.5 และคอมเมนต์ใน `01_Db.gs` เขียนตรงกันหมดว่า *"403 + code 42501"*
ซึ่ง**ไม่ตรงกับของจริง** · ผลคือ `dbDoorOfFailure_()` ตอบว่า `'KEY'` (คีย์ไม่ถูกยอมรับ)
ให้กับความล้มเหลวที่แท้จริงคือ `'GRANT'` — ส่งคนไปนั่งตรวจคีย์ที่ถูกต้องอยู่แล้ว
ซึ่งเป็นอาการที่คอมเมนต์ของฟังก์ชันนั้นเตือนไว้เองคำต่อคำ

**สามสาเหตุที่คืน 401 เหมือนกันหมด แยกได้ด้วย `code` ในbody เท่านั้น:**

| สาเหตุ | status | `code` | `message` |
| --- | --- | --- | --- |
| ไม่ส่ง apikey | 401 | ไม่มี | `No API key found in request` |
| apikey ใช้ไม่ได้ | 401 | ไม่มี | `Invalid API key` |
| **anon ที่ใช้ได้ แต่ยังไม่ GRANT** | **401** | **`42501`** | `permission denied for table work_order` |

→ **กฎที่ถูกคือ "ดู `code` ก่อนเสมอ ห้ามแยกด้วย status"** ไม่ใช่ "401 = คีย์ · 403 = GRANT"
→ ยังไม่ได้ยืนยันว่า `service_role` ให้ status เดียวกันไหม วัดด้วย anon เท่านั้น

### ข้อ 1 — 4xx อ่าน body ได้ไหม · **ได้**

- `fetch` อ่าน body ของ 4xx ได้ครบ แกะ JSON ได้ ได้ `code` `message` `hint` `details` ครบทุกช่อง
- `hint` มีชื่อตารางกับคำสั่ง SQL ติดมาด้วยจริง — **ยืนยันกฎข้อ 24 ว่าห้ามให้ไหลขึ้นหน้าเว็บ**
- คำขอแรกของ isolate ใช้ **790 ms** ที่เหลือ 4-6 ms — ตรงกับ 773 ms ที่กองที่ 0 วัดไว้

> **สองเคสในชุดนี้ไม่ได้ทดสอบสิ่งที่ชื่อมันบอก** — "ตารางที่ไม่มีอยู่จริง" กับ
> "เงื่อนไขผิดไวยากรณ์" ไม่ได้ส่งกุญแจไปด้วย จึงถูกปฏิเสธที่ประตูหน้าก่อน
> ทั้งคู่ได้ `No API key found` เหมือนกัน · ต้องแก้เครื่องวัดก่อนวัดซ้ำ

### ข้อ 2 — ความล้มเหลวทางเครือข่าย · **ต่างจาก `UrlFetchApp` อย่างสิ้นเชิง**

**`fetch` บน Worker ไม่โยนเลยสักกรณี** ทุกอย่างคืน Response ที่ Cloudflare สังเคราะห์ขึ้น

| สถานการณ์ | ผล | status | body |
| --- | --- | --- | --- |
| ชื่อโดเมนไม่มีอยู่จริง | คืน Response | **530** | `error code: 1016` |
| ใบรับรองไม่ตรงชื่อ | คืน Response | **526** | `error code: 526` |

> **เรื่องนี้ทำให้กฎข้อ 24 ใช้ไม่ได้ตามที่เขียนไว้** · กฎบอกว่า "ลองใหม่ได้เฉพาะ 5xx
> กับ timeout" · แต่โดเมนที่พิมพ์ผิดคืน **530 ซึ่งเป็น 5xx** แล้วลองใหม่กี่ครั้งก็
> ไม่มีวันสำเร็จ · `httpSend_` ต้องแยก 5xx ของปลายทางจริง ออกจาก 5xx ที่ Cloudflare
> สังเคราะห์ขึ้น (`1016` DNS · `526` ใบรับรอง) **ก่อน**ตัดสินใจลองใหม่

### ข้อ 4 — เพดานจำนวนคำขอย่อย · **50 ต่อการเรียกหนึ่งครั้ง**

```
สำเร็จ 50 → Error: Too many subrequests by single Worker invocation
```

| | |
| --- | --- |
| หน้ารายการงานแผนกเคยใช้ | **62 คำขอ → ตายแน่นอน** ไม่ใช่แค่ช้า |
| ลดเหลือแล้ว | 5 คำขอ |

> **แผน Workers Paid ไม่ใช่ของแถมอีกต่อไป** · SPEC 22.7 ตกลงจ่าย \$5 เพื่อปลดเพดาน
> CPU 10 ms · ตอนนี้มันปลดเพดานคำขอย่อยจาก 50 เป็น 1,000 ด้วย · **ถ้ายังอยู่บนแผนฟรี
> ทุกหน้าต้องอยู่ใต้ 50 ตลอดไป** และต้องมีตัวนับคอยเฝ้า ไม่ใช่อาศัยความจำ

### ข้อ 3 — เพดานเวลาของ `fetch` · **ไม่มีเพดานที่สั้นกว่า 35 วินาที**

| | ผล |
| --- | --- |
| ปล่อยค้าง 35 วินาที ไม่ใส่เพดานเอง | **คืน Response 200 ที่ 35,044 ms** · body มีเครื่องหมายว่า *ค้างครบแล้วตอบเอง* |
| ใส่เพดานเอง 3 วินาที | **โยน `DOMException` ชื่อ `TimeoutError`** ที่ 3,000 ms |

> **`httpSend_` ต้องใส่เพดานเวลาเอง** — เป็นงานที่ไม่เคยต้องทำบน Apps Script
> `fetch` รอจนปลายทางตอบ ไม่ว่าจะนานแค่ไหน · ปลายทางที่ค้างจึงลากคำขอของผู้ใช้
> ค้างตามไปด้วยจนกว่าแพลตฟอร์มจะฆ่าทั้งคำขอ

> **วัดได้แค่ "ไม่มีเพดานที่สั้นกว่า 35 วินาที" ไม่ใช่ "ไม่มีเพดานเลย"** · ถ้าอยากรู้
> ว่ามีเพดานที่ยาวกว่านั้นไหม ต้องวัดด้วยค่าที่ยาวกว่า — แต่ไม่จำเป็น เพราะยังไงเราก็
> ต้องใส่เพดานของเราเองที่สั้นกว่านั้นมากอยู่ดี

> **กฎที่แยกสองอย่างออกจากกันได้สะอาด** · เอาข้อนี้รวมกับข้อ 2 แล้วได้ว่า
> **โยน = การยกเลิกที่เราสั่งเอง · คืน Response = อย่างอื่นทั้งหมด** รวมทั้ง DNS พัง
> และใบรับรองพัง ซึ่งมาในรูป 5xx ที่ Cloudflare สังเคราะห์ขึ้น

### ข้อ 5 — Worker ลองใหม่ให้เองไหม · **ไม่ลอง**

```
ก่อนยิง hits = 0  →  ยิงหนึ่งครั้ง ได้ 500  →  หลังยิง hits = 1
```

> **กฎข้อ 24 ต้องเขียนเองทั้งหมด แพลตฟอร์มไม่ช่วยอะไรเลย** · ข่าวดีคือ
> **ไม่มีการลองใหม่ซ่อนอยู่** ที่จะยิงคำสั่งเขียนซ้ำโดยที่เราไม่รู้ ซึ่งอันตรายกว่ามาก
> ในตารางที่ห้ามลบอย่าง `Audit_Log`

### ข้อ 6 — body ที่ไม่อ่านจนจบ · **ไม่พัง ไม่ค้าง**

ทิ้ง body ขนาด 4 MB ไป 12 รอบติดกันโดยไม่อ่าน — ไม่พังสักรอบ ใช้เวลารวม 1,195 ms
แล้วรอบที่อ่านจนจบได้ครบ **4,194,304 ไบต์ ใน 66 ms**

> **ยังไม่ได้วัดกับปลายทางภายนอก** — วัดกับ Durable Object ซึ่งอยู่ในเครือข่ายของ
> Cloudflare เอง · body ที่ไม่อ่านจาก Supabase อาจไม่เหมือนกัน ถ้าเรื่องนี้สำคัญกับ
> การออกแบบเมื่อไร ต้องวัดซ้ำกับปลายทางจริง

### Durable Object แก้ปัญหา 1042 ได้จริง

รอบแรกทุกทางที่ยิง fetch ใส่ตัวเองได้ `404 error code: 1042` · เปลี่ยนเป้าเป็น
Durable Object ที่เรียกผ่าน stub แล้ววัดได้ครบทั้งสามข้อ

**ผลพลอยได้ที่สำคัญกว่าการหลบ 1042** — ตัวนับของข้อ 5 อยู่ใน object เดียวที่เรียก
ด้วยชื่อคงที่ ทุกคำขอจึงไปถึงตัวเดียวกันแน่นอน · ปัญหา "สามคำขอตกคนละ isolate"
**หายไปจริง ไม่ใช่แค่ถูกตรวจจับได้**

| 8 | อ่าน body ของ 4xx ได้ และแกะ `code` `message` `hint` `details` ได้ครบ | ข้อ 1 |
| 9 | **GRANT ที่ขาด → `401` พร้อม `code 42501`** ไม่ใช่ 403 | ข้อ 1 |
| 10 | ไม่ส่ง apikey / apikey ใช้ไม่ได้ → `401` **ที่ไม่มี `code`** | ข้อ 1 |
| 11 | คำขอแรกของแต่ละ isolate ช้ากว่าคำขออื่นมาก (790 ms เทียบ 4-6 ms) | ข้อ 1 |

> **ข้อ 7 คือข้อที่ของจำลองเดิมไม่มีทางมี** เพราะเพดานจำนวนคำขอย่อยไม่มีอยู่บน
> Apps Script เลย · ของจำลองต้องนับเองและโยนเมื่อถึง 50 ไม่งั้นหน้าที่ยิงเยอะ
> จะเขียวในเครื่องทุกครั้งแล้วตายบนของจริง — ซึ่งเกิดกับหน้ารายการงานแผนกมาแล้ว

### บทเรียนที่ใหญ่กว่าตัวเลขทุกตัวในหน้านี้

**สามครั้งในวันเดียวที่ `wrangler dev` ในเครื่องผ่าน แต่ของจริงไม่ผ่าน**

| # | เรื่อง | ในเครื่อง | ของจริง |
| --- | --- | --- | --- |
| 1 | สุ่มค่าที่ global scope | ผ่าน | ปฏิเสธตั้งแต่ deploy — `10021` |
| 2 | `.json()` ที่ไม่มีใครรับ error | ผ่าน | `1101` หน้าขาวไม่บอกอะไรเลย |
| 3 | ยิง `fetch` ใส่ตัวเอง | ผ่านสบาย | `1042` ทุกครั้ง |

นี่คือกฎข้อ 27 ในรูปที่จับต้องได้ที่สุดเท่าที่โปรเจกต์นี้เคยเก็บได้ · และเป็นเหตุผลว่า
ทำไม 22.10 ถึงห้ามสร้างของจำลองของ `fetch` จากอะไรนอกจากผลวัดของจริง

**สิ่งเดียวที่ `wrangler dev` พิสูจน์ได้คือ "เครื่องวัดทำงาน" ไม่ใช่ "คำตอบคืออะไร"**

### ของที่ต้องทำต่อ

1. แก้ `dbDoorOfFailure_()` ให้ดู `code` ก่อน status — **บั๊กที่ยังอยู่ในโค้ดวันนี้**
2. แก้ SPEC 22.2 · 22.5 และคอมเมนต์ใน `01_Db.gs` ทั้งสามจุดที่เขียนว่า 403
3. เพิ่มการแยก 5xx ของจริง ออกจาก 5xx ที่ Cloudflare สังเคราะห์ ใน `httpSend_`
4. ซ่อมเครื่องวัดข้อ 3, 5, 6 ให้เลิกพึ่งการยิงใส่ตัวเอง แล้ววัดใหม่
5. วัดว่า `service_role` ให้ status เดียวกับ anon ไหมตอน GRANT ขาด
6. บันทึกว่า Supabase กำลังเลิกใช้ legacy JWT key — กระทบ `01_Db.gs` โดยตรง

```
cd proof-batch1
npx wrangler deploy
npx wrangler secret put PROOF_TOKEN        # สุ่มยาว ๆ ไม่มีตัวนี้ Worker ปิดตาย
npx wrangler secret put SUPABASE_ANON_KEY  # anon เท่านั้น ห้าม service_role
curl -H "x-proof-token: <รหัส>" https://wo-probe-fetch.<ชื่อ>.workers.dev/body4xx
```

ทางที่ต้องยิงให้ครบหกทาง — `/body4xx` `/netfail` `/timeout` `/subrequests` `/retry` `/unread`
แล้ว **ลบ Worker กับความลับทิ้งทันทีที่วัดเสร็จ**

**อ่านก่อนเชื่อผลที่ได้**

- **`/body4xx` ที่ไม่ได้ตั้ง `SUPABASE_ANON_KEY` ตอบข้อ 1 ไม่ได้** เคสที่สำคัญที่สุด
  คือเคสที่กุญแจผ่านประตูหน้าเข้าไปแล้วถูกปฏิเสธที่ชั้น GRANT (`42501`) ซึ่งกุญแจปลอม
  ทำให้เกิดไม่ได้ · เครื่องวัดจะพิมพ์ว่า `ไม่ได้วัด` ในเคสนั้น ให้อ่านให้เห็น
- **`/retry` ประกาศตัวเองว่าวัดไม่ได้เมื่อสามคำขอตกคนละ isolate** ถ้าได้ `วัดไม่ได้ในรอบนี้`
  ให้ยิงซ้ำ ห้ามเอาตัวเลขจากรอบนั้นไปใช้
- **`/subrequests` ไต่ถึง 1,200 เป็นค่าปริยาย** เพราะหยุดที่ 60 แล้วไม่ชนอะไร
  จะได้คำตอบว่า "เกิน 60" ซึ่งตอบเรื่อง 62 คำขอของหน้ารายการงานแผนกไม่ได้ ·
  **ตัวเลขที่ได้เป็นของแผนที่บัญชีใช้อยู่ ณ วันวัด** ถ้าเปลี่ยนไป Workers Paid ต้องวัดใหม่
- **`/timeout` บอกเองว่าใครเป็นคนจบรอบนั้น** ฝั่งที่ค้างตอบเอง หรือมีใครฆ่ากลางทาง ·
  สองอย่างนี้ให้คำตอบตรงข้ามกันเรื่องการใส่เพดานเวลาใน `httpSend_`
